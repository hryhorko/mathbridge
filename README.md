# MathBridge EdTech

### Open Educational Ecosystem for Mathematical Computing

**MathBridge EdTech** is an open-source educational ecosystem that integrates a Learning Management System (ATutor) with interactive mathematical computing environments based on JupyterHub and SageMath.

The current implementation provides lightweight **JSON Web Token (JWT)-based Single Sign-On (SSO)** between ATutor and JupyterHub. The architecture is designed for university courses and small academic institutions where simple deployment, user isolation, and low administrative overhead are important.

The project is also used as a research platform for investigating the integration of learning management systems with interactive computational environments.

---

## Project Objectives

The main objectives of MathBridge are to:

* provide seamless Single Sign-On between ATutor and JupyterHub;
* provide students with access to interactive mathematical computing environments;
* support mathematical computations using SageMath and JupyterLab;
* isolate user environments using Docker containers;
* minimize infrastructure and administration requirements;
* provide an open-source and reproducible educational computing environment;
* support experimental research on LMS–computational environment integration.

---

## System Architecture

The current authentication and computing workflow is:

```text
                    ATutor LMS
                        │
                        │ JWT
                        ▼
                JupyterHub / TLJH
                        │
                 JWTAuthenticator
                        │
                 DockerSpawner
                        │
                        ▼
                Student Container
                        │
                 JupyterLab
                        │
                     SageMath
```

The ATutor module generates a short-lived JWT containing the authenticated ATutor username. JupyterHub validates the token and establishes the corresponding JupyterHub user session.

The implementation uses **HS256 (HMAC-SHA256)** for JWT signing and verification.

## Main Components

### ATutor `jupyter_auth`

A custom ATutor module providing the SSO entry point to JupyterHub.

The module:

* obtains the currently authenticated ATutor user;
* generates a short-lived JWT;
* redirects the user to JupyterHub;
* uses a shared secret for JWT signing;
* provides a simple configuration-based implementation suitable for small deployments.

Current release:

**`jupyter_auth 1.0.0`**

Source:

```text
atutor/jupyter_auth/
```

---

### JupyterHub JWT Authenticator

A custom JupyterHub authenticator validating JWT tokens generated by the ATutor module.

The authenticator:

* validates HS256 JWT signatures;
* extracts the username from the token;
* creates or authenticates the corresponding JupyterHub user;
* supports automatic login from ATutor;
* uses a custom login handler to correctly replace an existing JupyterHub login session when a different ATutor user authenticates in the same browser.

Source:

```text
jupyterhub/authenticator/
```

## Configuration

The ATutor module uses a lightweight configuration approach rather than a dedicated database configuration interface.

The main configuration is located in:

```text
atutor/jupyter_auth/include/config.inc.php
```

The configuration defines parameters required for communication with JupyterHub, including the JupyterHub endpoint and JWT-related settings.

The JupyterHub side is configured through the TLJH configuration mechanism:

```text
/opt/tljh/config/jupyterhub_config.d/
```

The corresponding authenticator configuration is represented in the repository by:

```text
jupyterhub/authenticator/20-jwt-auth.py
```

The JWT signing secret must be shared securely between the ATutor and JupyterHub components.

**Production deployments should not commit real JWT secrets to the repository.**

## Authentication Workflow

The SSO process consists of the following steps:

1. A student authenticates in ATutor.
2. The `jupyter_auth` module obtains the authenticated ATutor username.
3. ATutor generates a short-lived HS256-signed JWT.
4. The browser is redirected to JupyterHub with the JWT.
5. `JWTAuthenticator` validates the token.
6. The username contained in the JWT is mapped to the corresponding JupyterHub user.
7. JupyterHub establishes the user's authenticated session.
8. DockerSpawner starts or connects to the user's isolated computational environment.
9. The student accesses JupyterLab and SageMath without an additional login.

When another ATutor user authenticates in the same browser, the custom JupyterHub login handler forces the new JWT authentication to be processed and replaces the previous JupyterHub login session.

## Security Considerations

The current implementation is intentionally lightweight and is designed for controlled academic deployments.

The following security measures are used:

* HMAC-SHA256 JWT signatures;
* short-lived JWT tokens;
* server-side verification of JWT signatures;
* separation of authentication and user execution environments;
* Docker-based user isolation.

The JWT signing secret is a security-sensitive value and must be protected.

For production deployment, HTTPS should be used for all communication between the LMS, JupyterHub, and users.

The current implementation does not depend on an external OAuth 2.0 or OpenID Connect provider.

## Deployment Model

The current implementation is designed for deployment on a single Linux server or virtual machine.

The architecture intentionally avoids Kubernetes and other orchestration platforms for small academic deployments where the expected number of concurrent users is limited.

A typical deployment consists of:

```text
Ubuntu Server
│
├── ATutor
│   └── MySQL
│
├── The Littlest JupyterHub
│   ├── JWTAuthenticator
│   ├── DockerSpawner
│   └── Traefik
│
└── Docker
    └── Student computational containers
        └── SageMath / JupyterLab
```
