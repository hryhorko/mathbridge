Project Overview

MathBridge EdTech is an open-source academic research and development project focused on building a lightweight digital educational ecosystem for teaching mathematics and other STEM disciplines.

The project investigates practical ways to connect an existing Learning Management System (LMS) with an interactive computational environment while keeping authentication, administration, infrastructure requirements, and deployment complexity manageable for educational institutions.

Current Status:

The ATutor–JupyterHub integration prototype has been implemented and experimentally evaluated in an academic environment at Ternopil Ivan Puluj National Technical University (TNTU), Ukraine. The next planned stage is a broader cloud-based educational pilot.

Technical Contribution

The core technical contribution of MathBridge is a lightweight integration architecture connecting the ATutor LMS with the JupyterHub computational environment. The current prototype implements a Single Sign-On (SSO) mechanism based on JSON Web Tokens (JWT), allowing authenticated LMS users to access their Jupyter environments without a separate login. User computational environments are isolated using DockerSpawner.

The prototype was implemented and experimentally evaluated in an academic environment at Ternopil Ivan Puluj National Technical University (TNTU), Ukraine. The initial evaluation focused on authentication and environment-access latency, including the difference between cold-start and warm-start sessions.

The current architecture intentionally avoids dependence on an external OAuth2/OpenID Connect identity provider. The prototype uses a shared secret for JWT signing and verification between ATutor and JupyterHub.

Current Experimental Evidence

Academic deployment Initial implementation evaluated in the educational process of TNTU using small academic groups.
Computational environment JupyterHub with Docker-based isolation of user environments.
Performance focus Analysis of SSO access time and cold-start versus warm-start behavior.
Initial finding The main variation in total access time is associated with initialization of the computational environment, while the authentication component contributes a much smaller delay.

The current evidence is based on an initial academic deployment with limited infrastructure resources. It is therefore treated as preliminary experimental evidence rather than as a large-scale scalability evaluation.

Planned AWS Cloud Pilot

The next phase of the project is a cloud-based educational pilot designed to evaluate the MathBridge architecture under a broader real-world academic workload. The pilot is planned for approximately 50 engineering students at Ternopil Ivan Puluj National Technical University.

Target AWS Specifications

  • Compute: 1x Amazon EC2 m6i.2xlarge instance with 8 vCPUs and 32 GB RAM, providing resources for a single-node JupyterHub deployment with concurrent student environments.
  • Storage: 150 GB Amazon EBS gp3 SSD storage for the operating system, application data, JupyterHub configuration, and persistent user workspaces.
  • Planned utilization: approximately 120 hours/month, corresponding to scheduled university laboratory and practical sessions rather than continuous 24/7 operation.
  • Evaluation: concurrent access, cold/warm container startup behavior, resource utilization, system stability, and scalability limits of the selected single-node architecture.

The cloud pilot is intended to extend the existing local prototype and provide a broader experimental basis for evaluating its suitability for real educational workloads.

Why a Lightweight Architecture?

MathBridge is designed for educational settings where infrastructure and administrative resources may be limited. The current single-node architecture provides a practical balance between functionality, user isolation, resource requirements, and administrative simplicity.

The project does not currently aim to replace large-scale enterprise identity or cloud orchestration platforms. Instead, it investigates whether a simpler architecture can be sufficient for small and medium-sized academic groups.

Security Considerations

JWTs are signed using HMAC-SHA256 (HS256). The same shared secret must be configured independently on the ATutor and JupyterHub sides.

The actual shared secret is not committed to the public repository. Public configuration examples use placeholders rather than production credentials.

The current experimental deployment was conducted in a controlled environment. For deployment over an untrusted network, the JupyterHub endpoint should be protected using HTTPS/TLS. Short-lived JWTs are used to reduce the exposure window of an intercepted token.
