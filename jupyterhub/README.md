\# JupyterHub Component



\## Overview



The `jupyterhub/` directory contains the JupyterHub component of the MathBridge EdTech educational ecosystem.



JupyterHub provides the interactive computational environment used by students after authentication through the ATutor Learning Management System.



The JupyterHub component integrates:



\* JupyterHub for managing user sessions and computational environments;

\* a custom JWT authenticator for Single Sign-On from ATutor;

\* DockerSpawner for isolated user environments;

\* Traefik for HTTP routing and proxying;

\* SageMath and JupyterLab for mathematical computing.



The overall authentication and execution workflow is:



```text

ATutor LMS

&#x20;   │

&#x20;   │ JWT

&#x20;   ▼

JupyterHub

&#x20;   │

&#x20;   ├── JWTAuthenticator

&#x20;   │

&#x20;   ├── Traefik Proxy

&#x20;   │

&#x20;   └── DockerSpawner

&#x20;           │

&#x20;           ▼

&#x20;     User Container

&#x20;           │

&#x20;           ▼

&#x20;     SageMath / JupyterLab

```



\---



\## Role in MathBridge



JupyterHub is the computational component of the MathBridge ecosystem.



ATutor acts as the Learning Management System and provides the initial user authentication. After successful authentication, the ATutor `jupyter\_auth` module generates a short-lived JWT and redirects the user to JupyterHub.



JupyterHub validates the JWT using the custom `JWTAuthenticator` and establishes the corresponding JupyterHub user session.



DockerSpawner then provides an isolated computational environment for the authenticated user.



This architecture allows students to access mathematical computing tools without maintaining a separate JupyterHub username and password.

\## Architecture



The JupyterHub subsystem consists of several components with clearly separated responsibilities.

\## Authentication



Authentication is based on JSON Web Tokens (JWT).



The ATutor `jupyter\_auth` module is responsible for generating a signed JWT after the user has authenticated in ATutor.



The token contains the authenticated ATutor username and temporal claims such as `iat` and `exp`.



The token is signed using the HS256 algorithm.



JupyterHub uses the custom `JWTAuthenticator` to validate the token and extract the username.



The basic authentication sequence is:



```text

ATutor authentication

&#x20;       │

&#x20;       ▼

JWT generation

&#x20;       │

&#x20;       ▼

Browser redirect to JupyterHub

&#x20;       │

&#x20;       ▼

JWTAuthenticator

&#x20;       │

&#x20;       ├── signature validation

&#x20;       ├── token validation

&#x20;       └── username extraction

&#x20;       │

&#x20;       ▼

JupyterHub user session

```



Detailed information about the authenticator is available in:



```text

jupyterhub/authenticator/README.md

```

\## Shared JWT Secret



The ATutor and JupyterHub components use a shared JWT secret.



\*\*The secret configured in the JupyterHub JWT authenticator must be exactly identical to the secret configured in the ATutor `jupyter\_auth` module.\*\*



There is only one shared secret for the two components:



```text

ATutor jupyter\_auth

&#x20;       │

&#x20;       │ signs JWT

&#x20;       │

&#x20;       │ shared secret

&#x20;       ▼

&#x20;    JWT token

&#x20;       │

&#x20;       │

&#x20;       ▼

JupyterHub JWTAuthenticator

&#x20;       │

&#x20;       │ verifies JWT

&#x20;       │

&#x20;       │ same shared secret

&#x20;       ▼

Authenticated user

```



If the secrets are different, JupyterHub cannot verify the JWT signature generated by ATutor and authentication will fail.



The JWT secret is a security-sensitive value and must not be committed to the public repository.



For detailed configuration information, see:



```text

jupyterhub/authenticator/README.md

```

\## User Isolation



DockerSpawner is used to provide isolated computational environments for users.



Instead of running all users in the same Jupyter environment, each user can be assigned a separate Docker container.



Conceptually:



```text

Student 1 ──► Docker Container 1 ──► SageMath

Student 2 ──► Docker Container 2 ──► SageMath

Student 3 ──► Docker Container 3 ──► SageMath

```



This approach separates the users' computational environments and provides a practical level of isolation for the intended academic deployment.



DockerSpawner also makes it possible to define a common computational image for students while keeping individual notebook servers separate.

\## Mathematical Computing Environment



The computational environment is based on SageMath and JupyterLab.



SageMath provides tools for:



\* symbolic mathematics;

\* algebra;

\* calculus;

\* numerical computation;

\* equation solving;

\* mathematical visualization;

\* other computational mathematics tasks.



JupyterLab provides the interactive web-based environment in which students work with notebooks and computational tools.



The combination is intended for use in university mathematics courses and laboratory activities.

\## TLJH Deployment



The experimental deployment uses \*\*The Littlest JupyterHub (TLJH)\*\* as the JupyterHub installation and management environment.



The main JupyterHub configuration directory is:



```text

/opt/tljh/config/

```



Additional JupyterHub configuration files are loaded from:



```text

/opt/tljh/config/jupyterhub\_config.d/

```



The MathBridge deployment uses configuration files such as:



```text

10-dockerspawner.py

20-jwt-auth.py

```



The exact configuration may contain additional deployment-specific settings.



The repository contains the JWT authenticator source code, while deployment-specific configuration values should be configured on the target server.

\## Configuration Requirements



Before testing the integration, verify the following:



\### JupyterHub



\* JupyterHub is running;

\* the custom `JWTAuthenticator` is loaded;

\* the JWT authentication endpoint is accessible;

\* DockerSpawner is configured;

\* the required Docker image is available.



\### JWT



\* ATutor and JupyterHub use `HS256`;

\* the JWT contains the `username` claim;

\* the token contains appropriate temporal claims;

\* the JWT secret is identical on both sides.



\### Networking



\* JupyterHub is accessible from the user's browser;

\* the configured ATutor JupyterHub URL points to the correct endpoint;

\* HTTP/HTTPS routing is correctly configured;

\* the required proxy configuration is active.

\## User Switching



The integration supports switching between different ATutor users in the same browser.



For example:



```text

Browser session

&#x20;    │

&#x20;    ├── ATutor → user01

&#x20;    │       │

&#x20;    │       └── JupyterHub → user01

&#x20;    │

&#x20;    ├── ATutor logout

&#x20;    │

&#x20;    ├── ATutor → user02

&#x20;    │       │

&#x20;    │       └── JupyterHub → user02

&#x20;    │

&#x20;    └── Current JupyterHub identity → user02

```



This behavior is supported by the custom login handling implemented in the JWT authentication component.



It prevents a previous JupyterHub authentication session from incorrectly determining the identity of a subsequent ATutor user.

\## Security Considerations



The MathBridge JupyterHub architecture is designed for controlled academic deployments.



The authentication mechanism uses:



\* signed JWTs;

\* HS256;

\* a shared secret between ATutor and JupyterHub;

\* short-lived authentication tokens;

\* server-side token validation;

\* isolated Docker environments.



The JWT secret must be treated as a credential.



It must not be committed to the public GitHub repository.



For production deployments:



\* HTTPS should be used;

\* the JWT secret should be stored securely;

\* deployment-specific configuration should be separated from public source code;

\* access to the JupyterHub server should be restricted appropriately.

\## Design Rationale



The MathBridge deployment intentionally uses a lightweight architecture.



The current implementation does not require:



\* Kubernetes;

\* OAuth 2.0;

\* OpenID Connect;

\* an external identity provider;

\* a separate authentication microservice;

\* automatic horizontal scaling.



The architecture is intended for academic groups and university laboratories where a relatively small number of users can be supported by a single server.



Docker-based isolation provides separation between user computational environments while avoiding the additional operational complexity of a Kubernetes-based infrastructure.



\---



\## Limitations



The current JupyterHub implementation has been evaluated in the specific deployment environment described above.



The following areas have not been systematically evaluated:



\* large-scale multi-node deployment;

\* Kubernetes-based scaling;

\* high-availability JupyterHub deployment;

\* interoperability with external identity providers;

\* large concurrent user populations;

\* automatic cloud scaling.



The current architecture should therefore be considered a lightweight deployment model rather than a general-purpose large-scale JupyterHub platform.
