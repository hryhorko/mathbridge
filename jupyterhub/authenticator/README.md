# JupyterHub JWT Authenticator

## Overview

This directory contains the custom JWT-based authenticator used by the MathBridge EdTech project to authenticate users in JupyterHub through the ATutor Learning Management System.

The authenticator is designed for the MathBridge SSO architecture:

```text
ATutor
   │
   │ short-lived JWT
   ▼
JupyterHub
   │
   │ JWTAuthenticator
   ▼
JupyterHub user session
   │
   ▼
DockerSpawner
   │
   ▼
SageMath / JupyterLab
```

The implementation provides a lightweight authentication mechanism without requiring an external OAuth 2.0 or OpenID Connect identity provider.

## Authentication Model

The authenticator receives a JWT generated by the ATutor `jupyter_auth` module.

The token contains the username of the currently authenticated ATutor user.

A simplified token payload is:

```json
{
    "username": "student01",
    "iat": 1720000000,
    "exp": 1720000300
}
```

The timestamps shown above are examples. Actual values are generated at authentication time.

The token is signed using:

```text
HS256
```

The JupyterHub authenticator verifies the signature using the shared secret and extracts the `username` claim.

---

## JWTAuthenticator

The implementation defines a custom authenticator:

```python
class JWTAuthenticator(Authenticator):
```

The authenticator enables automatic login:

```python
auto_login = True
```

This means that JupyterHub does not display its normal login page as the first authentication step. Instead, the authentication flow is initiated through the configured JWT authentication endpoint.

---

## JWT Validation

The authentication process obtains the token from the request:

```python
token = handler.get_argument("token", None)
```

The token is then decoded and verified using the shared secret and the HS256 algorithm:

```python
payload = jwt.decode(
    token,
    SECRET,
    algorithms=["HS256"]
)
```

If the token cannot be validated, authentication is rejected.

The authenticator also verifies that the token contains the expected username claim:

```python
username = payload.get("username")
```

If the username is missing, authentication is rejected.

The username is returned to JupyterHub as the authenticated identity.

## JWT Secret Configuration

**The JWT secret in the JupyterHub authenticator must be exactly identical to the JWT secret configured in the ATutor `jupyter_auth` module.**

This is a mandatory requirement for the SSO integration.

The authentication mechanism uses one shared secret:

```text
ATutor jupyter_auth
        │
        │ signs JWT
        │
        │ HS256 + SECRET
        ▼
     JWT token
        │
        ▼
JupyterHub JWTAuthenticator
        │
        │ verifies JWT
        │
        │ HS256 + SAME SECRET
        ▼
Authenticated user
```

The ATutor module generates and signs the JWT using its configured secret.

The JupyterHub `JWTAuthenticator` verifies the received JWT using the value defined in:

```python
SECRET = "Edit me"
```

Therefore, the value of `SECRET` in `20-jwt-auth.py` **must be exactly the same value as the secret configured in the ATutor `jupyter_auth` module**.

For example, if the ATutor module is configured with:

```text
JUPYTERHUB_JWT_SECRET = my-production-secret
```

then the JupyterHub authenticator must use:

```python
SECRET = "my-production-secret"
```

Conversely, changing the secret on only one side will break authentication.

### Important

Do **not** generate two different secrets, one for ATutor and another for JupyterHub.

There must be **one shared JWT secret**:

```text
ATutor secret
      =
JupyterHub SECRET
```

If the values are different, the JupyterHub authenticator cannot verify the signature generated by ATutor and the authentication request will be rejected with:

```text
Invalid token
```

The actual production secret is a sensitive credential and **must not be committed to the public GitHub repository**.

The value shown in the repository source code:

```python
SECRET = "Edit me"
```

is only a placeholder. Before deployment, it must be replaced with the same secret configured for the ATutor `jupyter_auth` module.

## Configuration Consistency

Before starting the SSO integration, verify the following:

| Configuration    | ATutor              | JupyterHub                  |
| ---------------- | ------------------- | --------------------------- |
| JWT algorithm    | HS256               | HS256                       |
| JWT secret       | configured secret   | **exactly the same secret** |
| Username claim   | `username`          | `username`                  |
| Token expiration | generated by ATutor | validated by JWT processing |

The most important requirement is:

> **The ATutor JWT secret and the JupyterHub JWT secret must be identical.**

## Login Flow

The complete authentication process is:

```text
1. User authenticates in ATutor
            │
            ▼
2. User selects the JupyterHub integration
            │
            ▼
3. ATutor generates a JWT
            │
            ▼
4. Browser requests JupyterHub with the token
            │
            ▼
5. JWTAuthenticator validates the token
            │
            ▼
6. Username is extracted from the JWT
            │
            ▼
7. JupyterHub creates/authenticates the user
            │
            ▼
8. User is redirected to the JupyterHub environment
```

The user therefore does not need to enter JupyterHub credentials separately.

---

## Custom Login Handler

A custom login handler is included in the implementation to correctly handle authentication when the user changes between ATutor accounts in the same browser.

This behavior is important because JupyterHub maintains its own login cookie.

Without explicitly handling the new authentication request, an existing JupyterHub session can cause the browser to continue using the previously authenticated JupyterHub user.

The custom handler ensures that a new JWT authentication request is processed and the corresponding JupyterHub login session is updated.

---

## User Switching

The expected behavior is:

```text
Browser
   │
   ├── ATutor login: user01
   │       │
   │       └── JWT → JupyterHub → user01
   │
   ├── ATutor logout
   │
   ├── ATutor login: user02
   │       │
   │       └── JWT → JupyterHub → user02
   │
   └── JupyterHub session → user02
```

The implementation was specifically tested to address the case where the first user authenticates successfully and a second user subsequently authenticates using the same browser.

The second user must receive a JupyterHub session corresponding to the second ATutor username.

Testing in an anonymous/private browser session also confirmed the expected authentication behavior.

## JupyterHub Configuration

The authenticator is loaded through the TLJH configuration mechanism.

The deployment configuration directory is:

```text
/opt/tljh/config/jupyterhub_config.d/
```

The authenticator configuration file used by the deployment is:

```text
20-jwt-auth.py
```

The corresponding repository file is:

```text
jupyterhub/authenticator/20-jwt-auth.py
```

The TLJH configuration loader discovers Python configuration files from the `jupyterhub_config.d` directory.

The authenticator is selected using:

```python
c.JupyterHub.authenticator_class = JWTAuthenticator
```

and access is enabled for authenticated users using:

```python
c.Authenticator.allow_all = True
```

The exact deployment configuration may contain additional JupyterHub, DockerSpawner, or proxy settings that are outside the scope of this authenticator.

## Deployment

The repository file must be copied or otherwise deployed to the JupyterHub configuration directory.

For the TLJH deployment used in the MathBridge experiment:

```text
/opt/tljh/config/jupyterhub_config.d/20-jwt-auth.py
```

After changing the configuration, JupyterHub must be restarted so that the configuration is loaded.

A deployment administrator should verify that the running JupyterHub reports the expected authenticator.

The startup log should identify the custom authenticator rather than the default PAM authenticator.

## Security Considerations

The implementation is intentionally lightweight and intended for controlled academic deployments.

The following security properties are used:

* HS256 JWT signatures;
* a shared signing/verification secret;
* short-lived authentication tokens;
* server-side JWT verification;
* automatic authentication through JupyterHub.

The JWT secret is a security-sensitive value.

It must:

* be identical on the ATutor and JupyterHub sides;
* not be committed to a public repository;
* be protected on the server;
* be replaced if it is suspected of being compromised.

For production deployment, HTTPS should be used to protect the token during browser-based communication.

---

## Limitations

The current implementation deliberately does not use:

* OAuth 2.0;
* OpenID Connect;
* an external identity provider;
* Kubernetes;
* a separate authentication microservice.

The implementation is intended for lightweight deployments where ATutor and JupyterHub are operated within a controlled institutional environment.

Scalability and interoperability beyond the tested deployment configuration have not been systematically evaluated.

## Relationship to ATutor Module

The corresponding ATutor component is:

```text
atutor/jupyter_auth/
```

The two components must be configured consistently:

```text
ATutor jupyter_auth
        │
        │ JWT
        │
        ├── username
        ├── iat
        ├── exp
        └── HS256 signature
        │
        ▼
JupyterHub JWTAuthenticator
```

The ATutor module is responsible for generating the token.

The JupyterHub authenticator is responsible for validating the token and establishing the JupyterHub identity.

Neither component alone provides the complete SSO workflow.

## Troubleshooting

### JupyterHub starts with PAMAuthenticator

If the startup log reports:

```text
Using Authenticator: jupyterhub.auth.PAMAuthenticator
```

the custom configuration has not been loaded.

Check:

1. The file is located in the TLJH configuration directory.
2. The file has a `.py` extension.
3. The file is syntactically valid.
4. JupyterHub is started using the TLJH configuration.
5. JupyterHub has been restarted after configuration changes.

### Invalid token

If authentication fails with an invalid-token error, check:

1. The JWT secret in JupyterHub is **exactly identical** to the secret configured in the ATutor `jupyter_auth` module.
2. Both sides use `HS256`.
3. The JWT contains a `username` claim.
4. The token has not expired.
5. The token is being passed to the configured JupyterHub authentication endpoint.

### Wrong user after switching ATutor accounts

If JupyterHub continues to display the previous user:

1. Verify that the current `20-jwt-auth.py` is deployed.
2. Restart JupyterHub after changing the configuration.
3. Verify that the custom login handler is being used.
4. Test the sequence with two different ATutor accounts in the same browser.
5. Compare the result with a private/anonymous browser session.
